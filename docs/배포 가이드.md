# 배포 가이드

야구해 백엔드의 CI/CD 및 인프라 구성 문서입니다.

## 전체 구조

브랜치 전략은 `dev`(개발 통합) → `main`(배포)입니다.

```
기능 브랜치 ──PR──→ dev ──PR──→ main
                │              │
                │              └─ 푸시 ─→ CD (.github/workflows/cd.yml)
                │                          1. Docker 이미지 빌드 → GHCR 푸시 (latest, sha-<커밋>)
                │                          2. EC2로 compose 파일 + nginx 설정 전송
                │                          3. SSH 접속 → 이미지 pull → compose up
                │                          4. nginx -t 검사 후 reload
                │                          5. /api/v1/health/ready 헬스체크
                │                             (실패 시 로그 출력 후 실패 처리)
                │
                └─ dev/main 대상 PR·푸시 ─→ CI (.github/workflows/ci.yml)
                                             lint · format · build · unit test
                                             · e2e test · Docker 빌드 검증
```

즉 **`main`에 머지될 때만 실제 배포가 일어납니다.** `dev`는 CI 검증까지만 수행합니다.

EC2 안에서는 compose가 네 개의 서비스를 띄웁니다. 기동 순서는 `postgres` → `migration` → `app` → `nginx`이며, 각 단계가 정상일 때만 다음이 시작됩니다.

| 서비스 | 역할 |
|---|---|
| `postgres` | 운영 DB. 호스트 포트를 열지 않고 내부 네트워크로만 접근하며 데이터는 `yaguhae_pgdata` 볼륨에 유지 |
| `migration` | 앱보다 먼저 1회 실행되고 종료. `typeorm migration:run`으로 스키마 반영 |
| `app` | NestJS 앱. `migration`이 성공 종료한 뒤에만 기동. **호스트 포트를 열지 않고** nginx를 통해서만 접근됨 |
| `nginx` | 리버스 프록시. 외부에 노출되는 유일한 서비스(`HTTP_PORT`, 기본 80)이며 `app:4000`으로 전달 |

```
외부 ──80──→ nginx ──4000──→ app ──5432──→ postgres
             (유일한 노출 지점)   (내부 전용)    (내부 전용)
```

nginx 설정은 저장소의 [`nginx/conf.d/default.conf`](../nginx/conf.d/default.conf)에서 관리되며, 배포할 때마다 서버로 전송되고 `nginx -t` 문법 검사를 통과한 경우에만 reload됩니다. 검사에 실패하면 배포가 중단됩니다.

앱은 프록시 뒤에서 실행되므로 `main.ts`에서 `trust proxy`를 켜두었습니다. 따라서 `req.ip`와 프로토콜은 `X-Forwarded-*` 헤더의 실제 클라이언트 값으로 인식됩니다.

## 최초 1회: EC2 서버 준비

### 1. Docker 설치 (Amazon Linux 2023 기준)

```bash
sudo dnf install -y docker
sudo systemctl enable --now docker
sudo usermod -aG docker $USER   # 적용하려면 재접속 필요
```

Docker Compose v2 플러그인:

```bash
sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -SL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64 \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
docker compose version
```

### 2. 배포 디렉터리와 `.env` 생성

```bash
mkdir -p ~/yaguhae && cd ~/yaguhae
vi .env   # 아래 내용을 채운다
```

`.env` 내용은 저장소의 [`.env.production.example`](../.env.production.example)을 복사해서 값만 바꾸면 됩니다.

```dotenv
APP_IMAGE=ghcr.io/yaguhae/yaguhae_be:latest
HTTP_PORT=80
PORT=4000
NODE_ENV=production
CORS_ORIGIN=https://프론트엔드-도메인
DB_USERNAME=yaguhae
DB_PASSWORD=강력한-비밀번호
DB_DATABASE=yaguhae
JWT_ACCESS_SECRET=openssl-rand-hex-32-로-생성한-값
JWT_REFRESH_SECRET=위와-다른-값
SWAGGER_ENABLED=false
```

- `APP_IMAGE`는 배포 시 워크플로우가 커밋 SHA 태그로 덮어쓰므로 여기 값은 초기값/폴백입니다.
- `HTTP_PORT`는 nginx가 호스트에 노출할 포트입니다. `PORT`는 앱 컨테이너 내부 포트이므로 4000으로 고정합니다.
- `DB_HOST`, `DB_PORT`는 compose가 `postgres:5432`로 주입하므로 `.env`에 넣지 않습니다.
- `.env`는 서버에만 두고 저장소에 커밋하지 않습니다.
- `JWT_ACCESS_SECRET`·`JWT_REFRESH_SECRET`은 `openssl rand -hex 32`로 각각 생성합니다. **둘을 같은 값으로 쓰지 않습니다** — access 시크릿이 유출돼도 장기 세션(refresh)을 발급할 수 없게 분리한 것이 요점입니다.
- 시크릿을 교체하면 발급돼 있던 토큰이 전부 무효가 됩니다(전원 재로그인). 유출 대응 시에는 그것이 의도한 동작입니다.

### 3. 보안 그룹

| 포트 | 개방 여부 | 비고 |
|---|---|---|
| 22 (SSH) | 개방 | 배포용. GitHub Actions는 고정 IP가 아니므로 열어둘 범위를 팀에서 결정합니다 |
| 80 (HTTP) | 개방 | nginx가 받는 유일한 외부 포트 |
| 4000 | **열지 않음** | 앱은 호스트 포트를 열지 않고 nginx를 통해서만 접근됩니다 |
| 5432 | **열지 않음** | compose 내부 네트워크로만 접근합니다 |

## GitHub 설정

### Secrets (Settings → Secrets and variables → Actions → Secrets)

| 이름 | 설명 |
|---|---|
| `EC2_HOST` | EC2 퍼블릭 IP 또는 도메인 |
| `EC2_USER` | SSH 접속 계정 (Amazon Linux는 보통 `ec2-user`, Ubuntu는 `ubuntu`) |
| `EC2_SSH_KEY` | SSH 개인키 전체 내용 (`-----BEGIN ...` 줄 포함) |
| `EC2_PORT` | (선택) SSH 포트. 미설정 시 22 |

`GITHUB_TOKEN`은 GitHub가 자동으로 제공하므로 따로 등록하지 않습니다. 서버에서 GHCR 이미지를 받을 때도 이 토큰을 전달해 로그인하므로 별도의 PAT가 필요 없습니다.

### Variables (선택)

| 이름 | 설명 |
|---|---|
| `DEPLOY_PATH` | 서버 배포 디렉터리. 미설정 시 `~/yaguhae` |

`DEPLOY_PATH`는 **Secrets가 아니라 Variables 탭**에 등록해야 합니다. 워크플로우가 `vars.DEPLOY_PATH`로 참조하므로 Secrets에 넣으면 조회되지 않고 기본값으로 떨어집니다. 값은 `/home/ec2-user/yaguhae` 같은 절대경로를 권장합니다.

### 브랜치 보호 규칙 (권장)

CD는 `main` 푸시 시 CI 성공 여부와 무관하게 실행됩니다. 검증되지 않은 코드가 배포되지 않게 하려면 Settings → Branches에서 **`main`과 `dev` 두 브랜치 모두** 아래 규칙을 걸어두는 것을 권장합니다.

- Require a pull request before merging
- Require status checks to pass → `Lint & Test & Build`, `Docker 이미지 빌드 검증` 선택

이렇게 하면 CI를 통과한 PR만 머지되고, `main` 머지 시점에 CD가 실행됩니다.

## 배포 흐름

1. 기능 브랜치에서 작업 후 `dev`로 PR → CI가 검증 → 머지
2. 배포할 시점에 `dev` → `main` PR (릴리스 PR) 생성 → CI 재검증 → 머지
3. `main` 머지와 함께 CD 자동 실행
4. Actions 탭에서 `CD` 워크플로우 성공 여부 확인

수동 배포가 필요하면 Actions 탭에서 `CD` 워크플로우의 **Run workflow**를 실행합니다. 이때 실행 브랜치로 `main`을 선택해야 운영에 배포된 것과 동일한 코드가 나갑니다.

> 참고: 현재는 EC2 한 대에 운영 환경만 구성되어 있습니다. 나중에 스테이징 환경이 필요해지면 `dev` 푸시로 동작하는 워크플로우를 추가하고, 별도 서버(또는 다른 `HTTP_PORT` + compose 프로젝트 이름)로 배포하도록 분리하면 됩니다.

## 롤백

GHCR에 커밋 SHA 태그가 남아 있으므로, 서버에서 이전 이미지로 되돌릴 수 있습니다.

```bash
cd ~/yaguhae
export APP_IMAGE=ghcr.io/yaguhae/yaguhae_be:sha-<되돌릴-커밋-SHA>
docker compose -f docker-compose.prod.yml up -d
```

DB 마이그레이션까지 되돌려야 한다면 `pnpm migration:revert`에 해당하는 명령을 컨테이너에서 실행해야 합니다.

```bash
docker compose -f docker-compose.prod.yml run --rm migration \
  node_modules/.bin/typeorm migration:revert -d dist/database/data-source.js
```

## 운영 명령어

```bash
cd ~/yaguhae

docker compose -f docker-compose.prod.yml ps                 # 상태 확인
docker compose -f docker-compose.prod.yml logs -f app        # 앱 로그
docker compose -f docker-compose.prod.yml logs -f nginx      # nginx 접근/에러 로그
docker compose -f docker-compose.prod.yml restart app        # 앱 재시작 (.env 변경은 반영 안 됨)
curl http://127.0.0.1/api/v1/health/ready                    # nginx 경유 헬스체크
```

### `.env`(환경변수)만 바꿀 때

`restart`로는 반영되지 않습니다 — 기존 컨테이너를 그대로 살리기 때문에 `.env`를 다시 읽지 않습니다. 컨테이너를 다시 만들어야 합니다.

```bash
cd ~/yaguhae
vi .env
docker compose -f docker-compose.prod.yml up -d --force-recreate app
```

`.env`의 `APP_IMAGE`는 CD가 배포할 때마다 마지막 이미지 태그로 덮어쓰므로, 위 명령은 **지금 돌고 있는 것과 같은 이미지**로 다시 만듭니다.

> **`unauthorized` 에러가 난다면** `.env`의 `APP_IMAGE`가 서버에 없는 태그(예: 초기값 `:latest`)를 가리키고 있는 것입니다. 배포 스크립트는 마지막에 `docker logout ghcr.io`를 하므로 서버는 평소 비로그인 상태이고, 없는 이미지를 받으러 가면 반드시 실패합니다. 현재 태그를 확인해 직접 지정하면 pull 없이 재생성됩니다.
>
> ```bash
> docker compose -f docker-compose.prod.yml ps --format '{{.Image}}'
> APP_IMAGE=<위에서 확인한 태그> docker compose -f docker-compose.prod.yml up -d --force-recreate app
> ```

### nginx 설정만 바꿀 때

설정 파일은 볼륨 마운트라 컨테이너를 다시 만들 필요가 없습니다. 저장소에서 수정해 배포하면 CD가 자동으로 검사·reload하지만, 서버에서 직접 손볼 경우는 아래 순서를 지킵니다.

```bash
cd ~/yaguhae
vi nginx/conf.d/default.conf
docker compose -f docker-compose.prod.yml exec nginx nginx -t       # 반드시 먼저 검사
docker compose -f docker-compose.prod.yml exec nginx nginx -s reload
```

검사를 건너뛰고 reload하면 문법 오류 시 nginx가 죽어 서비스 전체가 중단됩니다. 또한 서버에서 직접 수정한 내용은 **다음 배포 때 저장소 버전으로 덮어써집니다.**

### DB 백업

같은 서버의 Docker Postgres를 사용하므로 백업은 직접 챙겨야 합니다. 최소한 아래 명령을 cron으로 걸어두는 것을 권장합니다.

```bash
docker exec yaguhae-postgres pg_dump -U yaguhae yaguhae | gzip > ~/backup/yaguhae-$(date +%F).sql.gz
```

## HTTPS로 전환하기

현재는 **도메인이 없어 HTTP(80)만 사용합니다.** 아래 준비는 이미 저장소에 반영돼 있어, 도메인만 확보하면 바로 켤 수 있습니다.

| 항목 | 상태 |
|---|---|
| ACME 챌린지 경로 (`/.well-known/acme-challenge/`) | ✅ nginx에 반영 |
| certbot 컨테이너 + 인증서 볼륨 | ✅ compose에 반영 (`certbot` profile) |
| 443 server 블록 | ✅ `nginx/ssl/api-ssl.conf.example`로 준비 |
| 443 포트 노출 | ✅ compose에 반영 |
| **도메인 + A 레코드** | ❌ **선행 조건** |

> **왜 도메인이 필수인가.** Let's Encrypt는 IP 주소에 인증서를 발급하지 않습니다. 도메인 없이는 이 절차를 시작할 수 없습니다.

### 0. 선행 조건

- 도메인 확보 (예: `api.도메인`을 API용 서브도메인으로 사용)
- **탄력적 IP(Elastic IP)** 할당 — 일반 퍼블릭 IP는 인스턴스를 중지·시작하면 바뀌어 A 레코드가 끊어집니다
- A 레코드를 그 IP로 연결하고 전파 확인:
  ```bash
  dig +short api.도메인
  ```
- 보안 그룹에 **443** 인바운드 추가 (80은 갱신 검증에 계속 필요하므로 **닫지 않습니다**)

### 1. `.env`에 도메인 기입

```dotenv
DOMAIN=api.도메인
CERTBOT_EMAIL=관리자@메일
HTTPS_PORT=443
```

### 2. 인증서 발급

nginx가 80으로 챌린지를 서빙하는 상태에서 실행합니다.

```bash
cd ~/yaguhae
set -a && source .env && set +a

docker compose -f docker-compose.prod.yml --profile certbot run --rm certbot \
  certonly --webroot -w /var/www/certbot -d "$DOMAIN" \
  --email "$CERTBOT_EMAIL" --agree-tos --no-eff-email
```

> **먼저 `--dry-run`을 붙여 한 번 돌려보세요.** Let's Encrypt는 도메인당 주 5회로 발급을 제한하는데, 오타나 DNS 미전파로 실패해도 횟수가 차감됩니다. dry-run은 제한에 포함되지 않습니다.

### 3. 443 활성화

발급이 성공한 **뒤에만** 파일 이름을 바꿉니다.

```bash
sed "s|\${DOMAIN}|$DOMAIN|g" nginx/ssl/api-ssl.conf.example > nginx/ssl/api-ssl.conf
docker compose -f docker-compose.prod.yml exec -T nginx nginx -t   # 반드시 먼저 검사
docker compose -f docker-compose.prod.yml exec -T nginx nginx -s reload
curl -I https://$DOMAIN/api/v1/health
```

> ⚠️ **인증서가 없는 상태에서 `.conf`로 두면 nginx가 기동에 실패해 서비스 전체가 멈춥니다.** `cannot load certificate ... No such file`로 죽습니다. 순서를 바꾸지 마세요.

### 4. 80 → 443 리다이렉트

443이 정상 동작하는 것을 확인한 다음에 `nginx/conf.d/default.conf`의 80 블록을 리다이렉트로 바꿉니다. **`/.well-known/acme-challenge/` location은 80에 남겨야 합니다** — 갱신 때마다 같은 경로로 다시 검증받습니다.

```nginx
server {
    listen 80;
    server_name _;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
        access_log off;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}
```

이 변경은 **저장소에서 수정해 배포**합니다. 서버에서 직접 고치면 다음 배포 때 덮어써집니다.

> 리다이렉트를 넣으면 컨테이너 헬스체크(`wget http://127.0.0.1/api/v1/health`)가 301을 받습니다. `--spider`는 301을 성공으로 처리하지만, 확실히 하려면 헬스체크를 `--max-redirect=0 http://127.0.0.1/api/v1/health` 대신 `https://127.0.0.1/...` + `--no-check-certificate`로 바꾸거나, 80 블록에 헬스체크 location을 예외로 남겨둡니다.

### 5. 자동 갱신

인증서는 90일마다 만료됩니다. cron에 등록합니다 (`crontab -e`):

```cron
0 4 * * 1 cd ~/yaguhae && docker compose -f docker-compose.prod.yml --profile certbot run --rm certbot renew --quiet && docker compose -f docker-compose.prod.yml exec -T nginx nginx -s reload
```

`renew`는 만료 30일 전부터만 실제로 갱신하므로 매주 돌려도 안전합니다. 갱신 후 **nginx reload를 반드시 붙여야** 새 인증서가 적용됩니다.

### 6. 애플리케이션 쪽 마무리

```dotenv
CORS_ORIGIN=https://프론트엔드-도메인
```

앱 코드는 수정할 게 없습니다 — `main.ts`에 `trust proxy`가 설정돼 있고 nginx가 `X-Forwarded-Proto`를 넘기므로 프로토콜을 올바르게 인식합니다.

> **auth 쿠키는 이 시점부터 정상 동작합니다.** 세션 쿠키가 `Secure` 속성으로 발급되기 때문에(운영 환경), HTTP에서는 브라우저가 저장을 거부합니다. **프론트와 로그인을 붙이기 전에 이 전환이 끝나 있어야 합니다.**

### 롤백

443에 문제가 생기면 `.conf`를 되돌리고 reload하면 즉시 80으로 돌아갑니다.

```bash
mv nginx/ssl/api-ssl.conf nginx/ssl/api-ssl.conf.disabled
docker compose -f docker-compose.prod.yml exec -T nginx nginx -s reload
```

## 배포 서버에서 API 문서 열기

Swagger UI는 **운영에서 기본적으로 닫혀 있습니다.** 스펙 문서는 모든 엔드포인트·파라미터·에러 코드의 지도라서, 공개하면 정찰 단계를 통째로 건네주는 셈이기 때문입니다.

열어야 한다면 서버의 `~/yaguhae/.env`에 세 값을 채우고 앱만 다시 띄웁니다:

```dotenv
SWAGGER_ENABLED=true
SWAGGER_USER=docs
SWAGGER_PASSWORD=충분히-긴-임의-문자열
```

```bash
cd ~/yaguhae
docker compose -f docker-compose.prod.yml up -d --force-recreate app
docker compose -f docker-compose.prod.yml logs app | grep Swagger
# → [Swagger] API 문서: /api/docs (Basic 인증 적용)
```

접속: `http://서버주소/api/docs` — 브라우저가 Basic 인증을 묻습니다.

| 상황 | 동작 |
|---|---|
| `SWAGGER_ENABLED` 미설정 | 운영이면 닫힘, 그 외에는 열림 (로컬 개발 기본값) |
| `SWAGGER_ENABLED=true` + 계정 있음 | Basic 인증을 걸고 엶 |
| `SWAGGER_ENABLED=true` + 계정 없음 | **열지 않고 에러 로그만 남김.** 부팅은 정상 — 문서 설정 하나로 API 전체가 내려가면 더 나쁩니다 |
| `SWAGGER_ENABLED=false` | 항상 닫힘 |

주의할 점:

- **경로에 `/api/v1`이 붙지 않습니다.** `setGlobalPrefix`는 컨트롤러 라우트에만 적용되고 Swagger UI는 별개라 `/api/docs`입니다. `/api/docs-json`·`/api/docs-yaml`도 같은 인증으로 보호됩니다.
- **HTTP 구간에서는 Basic 인증 자격이 평문으로 흐릅니다.** 현재 nginx는 80만 받으므로, 문서를 상시로 열어둘 계획이라면 "나중에 HTTPS로 전환하기"를 먼저 끝내는 편이 좋습니다.
- 프론트 개발용으로만 필요하다면 서버를 여는 대신 **저장소를 받아 로컬에서 `pnpm start:dev` 후 `/api/docs`를 보는 방법**이 더 안전합니다.
